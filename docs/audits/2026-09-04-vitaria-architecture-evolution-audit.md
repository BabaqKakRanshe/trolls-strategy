# Архитектурный аудит и анализ эволюции Vitaria

**Дата аудита:** 2026-09-04  
**Объект:** текущее состояние репозитория вместе с незакоммиченными изменениями  
**Методы:** анализ исходников, dependency graph, Git log/blame, churn/co-change, история локализации, тесты и проектная документация

## Краткий вердикт

Проект не страдает от классической «абстракции ради абстракции». Главная проблема
противоположна: хорошая декомпозиция низкоуровневых правил существует, но над ней нет единого
прикладного слоя. Поэтому все межсистемные сценарии, состояние мира, Phaser-представление и
развитие партии сошлись в одном 9 977-строчном `TownScene`.

1 сентября команда попыталась исправить это через `AlphaRun` и `AlphaTownScene`, но миграция
потеряла визуальную и интерактивную полноту. Через час runtime вернули к старой сцене. Новая
архитектура осталась рядом как параллельная модель, а документация и часть тестов продолжили
считать её основной.

Итог:

- runtime-истина находится в `TownScene`;
- headless-истина и проверка 20–30-минутного баланса находятся в неиспользуемом `AlphaRun`;
- документация утверждает обратное фактическому runtime;
- все quality gates зелёные, но они не обнаруживают этот архитектурный раскол.

Это главный системный риск проекта.

На момент аудита текущая рабочая копия проходит typecheck, ESLint и 1 020 тестов в 101 файле.
Проблема заключается не в общей неработоспособности, а в несовпадении runtime-модели,
тестируемой модели и архитектурной документации.

# 1. Фактическая архитектура

## 1.1. Runtime-поток

```text
main.ts
  → game.config.ts
    → scenes/index.ts
      → BootScene
        → PreloadScene
          → IntroScene
            → TownScene
```

`src/scenes/index.ts` импортирует именно старую `TownScene.ts`, а не `AlphaTownScene.ts`.

Фактическая схема приложения:

```text
TownScene
 ├─ Phaser lifecycle, карта, камера, input, animation, audio
 ├─ состояние партии и координация feature-сценариев
 ├─ Townhall / Villager / Production / Repair / Upgrades
 ├─ Population / Barter / Expedition / Chronicle
 ├─ Threat / CaveIn / Garrison / Cart / Pathing / Flock
 ├─ обучение, progression, финал, telemetry
 ├─ UI widgets
 ├─ config/balance + config/render + config/assets
 └─ localization + preferences + DEV bridge
```

Метрики `TownScene`:

- 9 977 строк;
- 248 методов;
- 70 import statements;
- 68 внутренних исходящих зависимостей;
- 109 затрагивающих её коммитов;
- наиболее частый co-change: `balance.ts` — 33 раза, `assets.ts` — 22, `render.ts` — 21,
  `PreloadScene.ts` — 14.

Класс одновременно является composition root, application service, world controller и
presentation controller.

## 1.2. Реальные слои

### `src/systems/`

Преимущественно чистые TypeScript-модели без Phaser. Здесь находятся локальные владельцы правил:
ресурсы, доставка, строительство, улучшения, население, события, угрозы и другие элементы
симуляции. Это настоящее и полезное разделение.

Исключение — `AlphaRun`: он импортирует `config/balance` и `config/alpha`, координирует всю
партию и по смыслу является application layer, хотя физически лежит в `systems`.

### `src/ui/`

Phaser-виджеты и presentation helpers. В основном они получают готовые данные или строки и не
владеют экономикой. Несколько UI-компонентов зависят от типов или presentation-состояния из
`systems`, что приемлемо, но подчёркивает отсутствие отдельного application contract.

### `src/entities/`

Небольшое количество Phaser-обёрток. Значительная часть относится к неактивной alpha-ветке и не
образует полноценный слой для текущей `TownScene`.

### `src/config/`

Три крупных глобальных реестра:

- `balance.ts` — правила и числа;
- `render.ts` — визуальные параметры;
- `assets.ts` — идентификаторы и описания ассетов.

Централизация полезна для inspector/bench, но ownership организован по техническому типу данных,
а не по feature.

### `src/utils/`

Чистая геометрия, маршруты, random, i18n, preferences и вспомогательные вычисления. В целом слой
остаётся листовым и не превратился в бесформенную свалку.

### `tools/`

Отдельное приложение инструментов: редакторы, инспектор, balance bench и asset pipeline. Оно
собирается отдельным Vite config и взаимодействует с игрой через ограниченный DEV bridge.

## 1.3. Направление зависимостей

Циклических импортов внутри `src` не найдено. Основное направление здоровое:

```text
scenes → systems/config/ui/utils
ui → config/utils/domain types
systems → types
```

Особые случаи:

- `config/game.config.ts → scenes/index.ts` — допустимая связь composition root;
- `AlphaRun → config` — признак того, что `AlphaRun` является прикладным координатором, а не
  элементарной системой;
- UI знает некоторые system-типы, потому что отдельного presentation/application contract нет.

## 1.4. Состояние и инфраструктура

- DI-контейнера, service locator и runtime singletons нет.
- Системы создаются сценой напрямую через конструкторы.
- Глобальное состояние ограничено Phaser cache, `localStorage` настроек и DEV-интерфейсом
  `window.town`.
- Сохранения партии отсутствуют.
- Networking/API отсутствуют.
- Кэширование — только asset/cache механизмы Phaser.
- Ошибки доменных инвариантов обрабатываются fail-fast исключениями.
- Недоступный `localStorage` безопасно деградирует в `null`.
- Отсутствующий перевод отображается ключом, что полезно при разработке.
- Логирование разделено на in-memory `Ledger` и DEV `console`.
- Межсценовой EventBus отсутствует сознательно: сейчас нет двух живых сцен, которым он нужен.

# 2. Восстановленная эволюция проекта

## 2.1. Первоначальный RTS-каркас — 18 августа

**Факт.** Первые коммиты создали классическую многосценовую архитектуру:

```text
Boot → Preload → Menu → Game + HUD overlay
```

Были созданы:

- `ResourceSystem`;
- глобальный типизированный `EventBus`;
- отдельные Game/HUD scenes;
- каталог будущих событий, большая часть которых имела payload `never`.

Ключевые коммиты: `6d984c8`, `ca5507b`, `d28ae0b`.

**Сильная гипотеза.** Планировалась расширяемая RTS с несколькими параллельными сценами,
реактивным HUD и универсальной событийной коммуникацией.

## 2.2. Смена самой игры — в тот же день

**Факт.** Коммит `d2d6b85` удалил RTS, `GameScene`, `HUDScene`, `MenuScene`, `ResourceSystem` и
EventBus. Сообщение коммита прямо говорит, что архитектура описывала игру, которой больше не
будет.

Первоначальное переусложнение было замечено чрезвычайно рано и удалено правильно.

## 2.3. Поселение и чистые системы — 18–19 августа

Появились:

- `ResourcePile`;
- `Townhall`;
- `Villager`;
- `Overheat`;
- `Repair`;
- новая `TownScene`.

Исходный подход был рационален для прототипа:

```text
маленькие чистые системы
        ↑
одна Phaser-сцена как composition root
```

Проблема возникла не в момент создания сцены, а когда composition root продолжил принимать
feature-логику после существенного роста проекта.

## 2.4. Взрыв ширины — 20–21 августа

За короткий период появились:

- склад и ограничения запаса;
- день/ночь и fog, позже частично удалённые;
- профессии;
- дальняя жила и повозка;
- события;
- торговля;
- еда и охота;
- экспедиции;
- гоблины и казармы;
- pathfinding;
- pause/settings;
- восемь языков.

**Сильная гипотеза.** Скорость добавления vertical features была выше скорости формирования их
границ. Каждая отдельная система оставалась небольшой и тестируемой, но их взаимодействия
добавлялись непосредственно в сцену.

## 2.5. Локальные исправления укрепляют сцену — 21–31 августа

Git blame показывает постепенное присоединение независимых областей:

- торговля — `72149fd`;
- экспедиции — `3c8aab4`;
- события — `697ac3`;
- рейды — `8c07165`;
- cave-in — `43d7399`;
- militia lifecycle — `aeb6b52`.

Получилась характерная цепочка:

```text
сцена связывает две системы
→ появляется третья система
→ переходные состояния остаются в сцене
→ UI требует дополнительных полей
→ frame loop координирует всё
→ тесты начинают читать текст сцены
→ сцена становится архитектурной границей
```

## 2.6. Попытка создать application layer — 1 сентября

- `36567b5`: создан 746-строчный детерминированный `AlphaRun`;
- `126590f`: runtime переключён на `AlphaTownScene`;
- `180bcfa`: примерно через час runtime возвращён на старую `TownScene`.

Причина возврата документирована: новое представление не сохранило старый UI, анимированных
жителей, физические мешки, audio и другие игровые связи.

Это было разумное оперативное решение, но follow-up по завершению миграции не произошёл.

## 2.7. Параллельные архитектуры — 1–3 сентября

`AlphaRun`, `AlphaTownScene`, `AlphaUi` и их тесты остались. Старую сцену продолжили развивать.
Коммит `a84832e` изменил `TownScene` ещё на 1 540 строк.

Так временный rollback стал постоянной архитектурой.

## 2.8. Языковой scope oscillation — 3–4 сентября

- `ed7bd15`: runtime сведён к английскому, 284 строки удалены;
- текущая рабочая копия восстанавливает выбор восьми языков;
- `GAME.md` всё ещё утверждает, что runtime только английский.

Это не провал i18n-механизма, а рассинхронизация продуктового решения, кода и документации.

# 3. Основные архитектурные проблемы

## Две параллельные модели одной партии

**Severity:** High  
**Тип:** Evolution Debt / Duplicate Architecture / Missing Boundary

**Где:** `src/scenes/TownScene.ts`, `src/systems/AlphaRun.ts`,
`src/scenes/AlphaTownScene.ts`, alpha UI и связанные тесты.

**Что произошло:** runtime использует старую модель, а headless simulation, часть UI-моделей и
тест баланса используют `AlphaRun`.

**Как это, вероятно, появилось:** правильную по направлению миграцию сделали как замену
presentation целиком. После потери визуального качества runtime откатили, но новую ветку не
удалили и не встроили.

**Доказательства:**

- `126590f` переключил registry на `AlphaTownScene`;
- `180bcfa` переключил его обратно;
- `tests/unit/alpha-scene-contract.test.ts` теперь явно запрещает активировать
  `AlphaTownScene`;
- `tests/unit/alpha-run-progression.test.ts` измеряет `AlphaRun`, а не runtime;
- `GAME.md` ошибочно называет `AlphaRun` владельцем партии.

**Почему это проблема:** баланс, progression и команды могут расходиться между двумя
реализациями, сохраняя зелёные тесты.

**Последствия:** ложная уверенность в балансе, двойная стоимость изменений, непонятный владелец
правил, риск исправить баг только в одной модели.

**Как должно было быть спроектировано изначально:** сначала command/snapshot boundary под
существующей `TownScene`, затем переключение по одному vertical slice с сохранением прежнего
представления.

**Что делать сейчас:** выбрать одну каноническую модель. Реалистичный путь — оставить текущую
визуальную сцену, но постепенно перевести её на session/controller, основанный на полезных
принципах `AlphaRun`.

**Стоит ли исправлять:** Да. Это основной источник ложной уверенности.

## `TownScene` стала God Object

**Severity:** High  
**Тип:** God Object / Coupling / Missing Application Layer

**Где:** `src/scenes/TownScene.ts`.

**Что произошло:** класс одновременно владеет игровым состоянием, порядком тиков,
межсистемными workflow, картой, Phaser-объектами, input, UI, audio, tutorial, progression,
finale, telemetry, localization, settings и DEV-интерфейсом.

**Как это, вероятно, появилось:** сцена была разумным composition root для одной шахты и одного
жителя. Каждая новая feature добавляла чистую систему, но состояние связи между системами
оставалось в сцене.

**Доказательства:** 9 977 строк, 248 методов, fan-out 68, 109 изменяющих коммитов. В одном
`tickWorld()` координируются calendar, ledger, chronicle, tutorial, trade, food, expedition,
raid, fatigue, production, flock и workers.

**Почему это проблема:** причин изменения гораздо больше одной. Изменения разных features
конфликтуют в одном файле, а полную партию нельзя воспроизвести без Phaser.

**Последствия:** высокая стоимость onboarding, сложные merge conflicts, source-level tests,
риск порядка обновления, практически невозможный полноценный save/load.

**Как должно было быть спроектировано изначально:** сцена могла оставаться единственной
Phaser-сценой, но должна была делегировать progression и workflows объекту `GameSession` или
`TownRun`.

**Что делать сейчас:** не делить файл механически по числу строк. Сначала вынести владельца
состояния и команды, затем world presentation adapters, затем feature-specific presenters.

**Стоит ли исправлять:** Да, инкрементально.

## Тесты закрепляют реализацию вместо поведения

**Severity:** High  
**Тип:** Test Architecture / Evolution Debt

**Где:** `alpha-scene-contract`, `bridge-gate`, `chronicle`, `hud-contract`, `teach-goals`,
`tooltip-contract`, `upgrades` и другие source-contract tests.

**Что произошло:** часть тестов читает `TownScene.ts` через `readFileSync` и проверяет наличие
строк, вызовов или фрагментов реализации.

**Как это, вероятно, появилось:** `TownScene` нельзя полноценно поднять в jsdom. Source-contract
tests стали дешёвым способом удерживать багфиксы.

**Доказательства:** несколько тестов загружают исходный код сцены и проверяют `toContain`, regex
или относительный порядок методов. `alpha-scene-contract` прямо фиксирует конкретный импорт.

**Почему это проблема:** наличие текста не доказывает поведение, но мешает безопасно изменить
структуру. Тесты превращают внутреннюю реализацию монолита в публичный контракт.

**Последствия:** ложноположительные проверки, хрупкий refactoring, архитектурная инерция.

**Как должно было быть спроектировано изначально:** чистые workflow-тесты для session/controller
плюс небольшой набор Playwright-тестов на реальную интеграцию Phaser.

**Что делать сейчас:** классифицировать source tests. Asset/static-policy проверки оставить;
behavioral regex-проверки заменять по мере извлечения соответствующих workflow.

**Стоит ли исправлять:** Да, одновременно с декомпозицией, а не отдельной массовой переписью.

## Feature-код вне текущего alpha scope остаётся внутри runtime

**Severity:** Medium–High  
**Тип:** Historical Debt / Cohesion / Architecture Fossils

**Где:** торговля, еда, expeditions, raids, garrison, cave-in, cart и chronicle внутри
`TownScene` и `balance.ts`.

**Что произошло:** `GAME.md` говорит, что эти области не входят в путь первой альфы, но активная
сцена всё ещё создаёт и тикает их.

**Как это, вероятно, появилось:** scope первой альфы был сужен после реализации более широкой
игры. Фичи отключили через progression/gating, а не вывели из активного runtime.

**Доказательства:** `TownScene` создаёт `Barter`, `Expedition`, `Chronicle`, `Threat`, `CaveIn`,
`Garrison`, `Cart` и их временное presentation-state. `tickWorld()` продолжает учитывать
несколько из этих подсистем.

**Почему это проблема:** критический путь зависит от файла с множеством необязательных
подсистем. Простое изменение текущей альфы несёт риск регрессии отложенного контента.

**Последствия:** лишняя связанность, большая матрица состояний, повышенная цена тестирования.

**Как должно было быть спроектировано изначально:** optional features подключаются через feature
manifest или отдельные coordinators, а не существуют как поля основного класса.

**Что делать сейчас:** для каждой области принять решение `alpha`, `post-alpha` или `delete`.
Неактивное удалить либо изолировать за явным feature module.

**Стоит ли исправлять:** Да, после выбора канонической модели.

## Глобальные config-файлы стали вторичными hotspots

**Severity:** Medium  
**Тип:** Coupling / Cohesion / Shared-Core Growth

**Где:** `src/config/balance.ts`, `src/config/render.ts`, `src/config/assets.ts`.

**Что произошло:** конфигурация вынесена из логики правильно, но сгруппирована по техническому
виду, а не по feature ownership.

| Файл         | Строк | Коммиты | Fan-in |
| ------------ | ----: | ------: | -----: |
| `balance.ts` | 1 105 |      59 |      5 |
| `render.ts`  |   802 |      42 |     32 |
| `assets.ts`  |   877 |      41 |     15 |

**Как это, вероятно, появилось:** собственные inspector/bench требуют централизованного доступа,
поэтому реестры постепенно расширялись.

**Доказательства:** высокая частота совместных изменений с `TownScene`; многие UI-компоненты
зависят от общего `render.ts`.

**Почему это проблема:** feature-изменение часто затрагивает сцену сразу с balance, render и
assets. Файлы становятся общей зоной конфликтов.

**Последствия:** слабое ownership, трудное удаление feature, высокая вероятность случайных
зависимостей.

**Как должно было быть спроектировано изначально:** feature-owned config с агрегирующим индексом
для инструментов.

**Что делать сейчас:** не разрушать inspector. Сначала ввести экспортирующие фасады:

```text
features/<feature>/{rules,render,assets}.ts
config/balance.ts → registry/re-export для инструментов
```

**Стоит ли исправлять:** Возможно. После разгрузки `TownScene`; сейчас это не первопричина.

## Отсутствует сериализуемый владелец состояния партии

**Severity:** Medium сейчас / High при продолжении incremental-направления  
**Тип:** Missing Architecture / Persistence Boundary

**Где:** состояние распределено между `TownScene`, чистыми системами и Phaser-объектами.

**Что произошло:** сейвы сознательно не реализованы, но состояние сцены уже включает
многочисленные временные списки, ссылки на sprites, timers и переходные фазы.

**Как это, вероятно, появилось:** текущая alpha рассчитана на один присест, поэтому persistence
не было немедленным требованием.

**Доказательства:** `GAME.md` прямо фиксирует отсутствие сейвов, одновременно признавая, что
incremental-игра без них не живёт. `AlphaRun` умеет отдавать snapshot, но не является runtime и
не имеет полноценного restore.

**Почему это проблема:** добавить `save/load` поверх текущей модели почти невозможно без
неполного сохранения или копирования правил.

**Последствия:** блокировка длинной прогрессии, сложные миграции формата, риск потери состояния.

**Как должно было быть спроектировано изначально:** одна сериализуемая snapshot-модель; Phaser-
состояние восстанавливается из неё, но не входит в неё.

**Что делать сейчас:** до первого сейва определить стабильные IDs сущностей, версионированный
`GameSnapshot`, `restore(snapshot)` и различие persistent/transient state.

**Стоит ли исправлять:** Да, до расширения длительности партии. Для текущего alpha это не
production bug.

## Архитектурная документация содержит взаимоисключающие истины

**Severity:** High для agent-driven проекта  
**Тип:** Documentation Debt / Governance

**Где:** `GAME.md`, `ai/context/code-map.md`, `docs/tdd/00-architecture.md`, `CLAUDE.md`.

**Что произошло:** `GAME.md` и `code-map.md` утверждают, что владельцем является `AlphaRun`,
runtime использует `TownScene`, а `00-architecture.md` признаёт состояние в сцене. Текущий код
снова поддерживает восемь языков, но `GAME.md` говорит «только английский».

**Как это, вероятно, появилось:** документация была обновлена для нового cutover, но rollback
изменил только registry и focused tests.

**Доказательства:** Git blame связывает утверждения про `AlphaRun` с коммитом `5c03da9`, тогда
как `src/scenes/index.ts` был возвращён к `TownScene` коммитом `180bcfa`.

**Почему это проблема:** документы используются как инструкции для следующих AI-изменений.
Ошибка воспроизводится автоматизированно и быстро.

**Последствия:** неверные планы, правки неактивного кода, повторные архитектурные откаты.

**Как должно было быть спроектировано изначально:** один authoritative architecture snapshot,
остальные документы ссылаются на него и явно отмечают intended/future state.

**Что делать сейчас:** обновить фактическую карту, пометить alpha-ветку experimental/inactive и
добавить простую автоматическую проверку выбранной runtime scene.

**Стоит ли исправлять:** Да, немедленно. Это дешёвое исправление с большим эффектом.

# 4. Localization/i18n как case study

## 4.1. Была ли локализация предусмотрена изначально

**Факт:** да. Двухъязычный `config/i18n.ts` появился 18 августа в `0b1aa30`, до первой
полноценной `TownScene`.

При этом самый ранний `MenuScene` содержал hardcoded `Начать игру`, а первая `TownScene` —
hardcoded `Перегрев!`. Следовательно, boundary был предусмотрен, но миграция UI шла по мере
появления компонентов.

## 4.2. Эволюция

```text
18 августа: ru/en config и locale assets
→ первые компоненты частично hardcoded
→ translate(dict, dotted.key, params)
→ 21 августа: persisted preference и URL/browser/saved resolution
→ 21 августа: восемь языков
→ новые feature-строки добавляются во все словари
→ 3 сентября: runtime English-only, корпус переводов сохранён
→ текущая working tree: восстановление восьми языков
```

Representative examples:

- `Начать игру` в раннем `MenuScene` → locale-driven menu;
- `Перегрев!` в ранней `TownScene` → ключ `town.overheated`;
- два языка → восемь (`80531c8`) → удалённый picker (`ed7bd15`) → текущий
  восстановленный picker.

## 4.3. Текущее качество

Сделано хорошо:

- domain/systems не знают о локализации;
- все языки сверяются по набору ключей;
- есть параметризация строк;
- неизвестный ключ виден на экране;
- самоназвания языков не зависят от текущего языка;
- `localStorage` отказоустойчив;
- URL override, сохранённый выбор и fallback централизованы.

Добавить язык технически легко: код, самоназвание и JSON. Основная стоимость — перевод полного
словаря.

Сменить механизм на live switching труднее: словарь читается сценами из Phaser cache, а текущая
смена языка выполняется через сохранение и reload.

**Вывод:** поздняя локализация не создала основной долг. Источник долга — колебание продуктового
решения и несинхронная документация. Текущая незакоммиченная реализация архитектурно ближе к
исходному замыслу.

# 5. Overengineering и underengineering

## 5.1. Первоначальное переусложнение

1. Типизированный EventBus с каталогом будущих событий до появления реальных слушателей. Удалён
   в тот же день — правильное решение.
2. Пять сцен для экономики из одного `ResourceSystem`. Также удалены после смены игры.
3. `AlphaTownScene` как новая presentation целиком вместо адаптации старой — слишком большой
   миграционный шаг.
4. Параллельные `AlphaUi` и models после rollback — гибкость используется тестами, но не игрой.
5. Часть source-contract tests — сложный substitute для отсутствующей тестируемой границы.

Собственные редакторы и asset pipeline не являются однозначным overengineering: они реально
используются, отделены отдельным Vite config и имеют тесты.

## 5.2. Изначально недопроектировано

1. Не было application/session boundary над чистыми systems.
2. Не был определён момент, когда composition root должен перестать владеть feature state.
3. Не было migration seam между domain и богатым Phaser-представлением.
4. Не была предусмотрена сериализация партии.
5. Не существовало single source of truth для архитектурной документации.

# 6. Essential и accidental complexity

## 6.1. Essential complexity

- физический жизненный цикл ресурса: выпуск → земля → бронь места → перенос → склад;
- сохранение ноши при смене назначения;
- pathfinding вокруг динамических препятствий;
- детерминированные RNG streams;
- порядок тиков для raid, fatigue, worker movement и UI feedback;
- визуальная синхронизация спрайтов с экономикой.

`Villager.ts` большой — 871 строка, — но имеет только три импорта и остаётся связанным вокруг
одной сложной state machine. Это не первоочередной God Object.

## 6.2. Accidental complexity

- два владельца правил партии;
- feature orchestration внутри Phaser scene;
- inactive features в active composition;
- тестирование исходного текста;
- документация, описывающая отменённый cutover;
- технически сгруппированные shared configs.

## 6.3. Historical debt

- `TownScene` была адекватной маленькому прототипу, но перестала быть адекватной после взрывного
  роста features;
- rollback к старой presentation был разумен в момент появления, но должен был сопровождаться
  планом завершения migration;
- post-alpha features были рабочим продуктовым экспериментом, но после сужения scope стали
  архитектурными окаменелостями.

## 6.4. Premature architecture

- первоначальный EventBus и каталог будущих событий;
- начальная многосценовая схема без реальной межсценовой сложности;
- полная новая presentation до обеспечения feature parity.

## 6.5. Missing architecture

- application/session boundary;
- сериализуемое состояние;
- feature ownership;
- поведенческий integration-test seam;
- единый authoritative architecture document.

# 8. Архитектурная ретроспектива

## 8.1. Первоначальный замысел

Типизированная Phaser-архитектура с чистой экономикой, несколькими сценами и EventBus. После
смены игры замысел упростили до одной сцены и чистых систем.

## 8.2. Что изначально было переусложнено

Будущие события и многосценовая композиция до появления реальной потребности; позже — big-bang
замена presentation через `AlphaTownScene`.

## 8.3. Что изначально было недопроектировано

Владелец полной партии, feature boundaries и сериализация.

## 8.4. Ключевые поворотные моменты

1. Создание RTS-каркаса.
2. Полное удаление старой игры в тот же день.
3. Создание `TownScene` как простого composition root.
4. Добавление широкого набора features 20–21 августа.
5. Рост source-level contract tests.
6. Создание `AlphaRun`.
7. Неудачный presentation cutover.
8. Возврат к старой сцене без завершения миграции.
9. English-only и текущее восстановление локализации.

## 8.5. Как накапливался technical debt

```text
одна сцена удобна для прототипа
→ чистые системы снимают локальные правила
→ межсистемное состояние остаётся в сцене
→ каждая feature добавляет поля и ветки tick loop
→ сцену нельзя тестировать без Phaser
→ тесты начинают читать её исходник
→ рефакторинг создаёт вторую модель
→ presentation теряет parity
→ runtime откатывают
→ обе модели остаются
→ документация и тесты расходятся с runtime
```

## 8.6. Главные архитектурные ошибки

1. Миграция application layer через замену presentation.
2. Отсутствие единого runtime/headless владельца партии.
3. Закрепление монолита source-contract tests.
4. Сохранение post-alpha features в active composition.
5. Отсутствие дисциплины удаления отменённой архитектуры.

## 8.7. Что было сделано правильно

- строгий TypeScript;
- чистые systems без Phaser;
- детерминированный RNG;
- локальные state owners вроде `Townhall`, `ResourcePile`, `Repair`;
- отсутствие ненужного EventBus;
- независимые UI widgets;
- богатое автоматизированное тестирование;
- атомарная и хорошо описанная Git-история;
- отдельный runtime/tooling build;
- i18n keyset validation.

## 8.8. Что выглядит плохо, но на самом деле оправдано

- одна Phaser scene для текущего масштаба сама по себе нормальна;
- большие `Villager` и pathing отражают реальную доменную сложность;
- большие typed config registries частично оправданы inspector/bench;
- отсутствие saves допустимо для одноразовой 20–30-минутной alpha;
- отсутствие DI и EventBus — преимущество, а не недостаток.

## 8.9. Архитектура, которая была бы оптимальной

```text
Phaser Scenes
  └─ TownPresentation
       ├─ Input adapter
       ├─ World renderer
       └─ UI presenters
              ↓ commands / snapshots / events
         GameSession
           ├─ Economy
           ├─ Workforce
           ├─ Construction
           ├─ Progression
           └─ Optional feature coordinators
              ↓
         Pure domain systems
```

Одна игровая сцена, без DI framework и глобальной шины. Нужен только сериализуемый
`GameSession`.

## 8.10. Архитектура, к которой стоит двигаться сейчас

1. Объявить `TownScene` текущим runtime, а `AlphaRun` — migration prototype.
2. Запретить добавление новых правил непосредственно в сцену.
3. Ввести `GameSession` с `command/tick/snapshot`, не меняя существующий UI.
4. Первым перенести production/resource delivery.
5. Затем construction/workforce.
6. Затем progression/tutorial/finale.
7. Заменить соответствующие source-contract tests behavioural-тестами.
8. Добавить browser smoke tests визуальной parity.
9. После parity удалить `AlphaTownScene` и дублирующие UI/models либо сделать новый session их
   единственным источником.
10. Только затем дробить config по feature ownership и проектировать save schema.

# 10. Дополнительные выводы аудитора

## 10.1. Главная проблема — не размер класса, а отсутствие уровня решений

Между маленькими моделями правил и engine scene отсутствует слой, который отвечает на вопросы:

- какая команда сейчас допустима;
- какие системы должны измениться вместе;
- в каком порядке применяется результат;
- что является полным состоянием партии;
- какое событие увидит presentation;
- что должно попасть в save.

Пока этот слой отсутствует, любое деление `TownScene` на несколько файлов будет косметическим.
Большой класс превратится в несколько managers с тем же общим состоянием и неявным порядком.

## 10.2. `AlphaRun` доказал направление, но не доказал миграционный подход

`AlphaRun` показал, что headless-партия, команды и snapshots возможны. Ошибка заключалась не в
самой модели, а в попытке одновременно заменить модель и presentation. В дальнейшем нужно
сохранять работающий внешний слой и менять источник его данных постепенно.

## 10.3. Скорость разработки стала архитектурным фактором

503 коммита за короткий период и большое количество хорошо описанных локальных решений дали
высокую скорость, но локальная доказательность не сложилась в глобальную архитектуру.
Следовательно, проекту нужны не дополнительные общие правила, а автоматические checkpoints:

- кто владеет состоянием;
- какой runtime-путь активен;
- не появилось ли второй реализации правила;
- может ли новая feature быть протестирована без presentation;
- обновлена ли factual architecture map.

## 10.4. Документация здесь является исполняемой частью архитектуры

В agent-driven разработке неверный Markdown опаснее обычного устаревшего комментария: следующий
агент использует его как спецификацию и распространяет ошибку. Архитектурные документы следует
версионировать и проверять почти так же строго, как публичные интерфейсы.

## 10.5. Следующий крупный feature должен быть архитектурным тестом

Не стоит сначала полностью рефакторить проект, а затем продолжать разработку. Следующую реальную
feature нужно провести через новый session boundary. Если для неё не приходится добавлять
domain-state в scene, граница работает. Если приходится — контракт недостаточен.

# 11. Универсальные best practices для будущих AI-агентов

Этот раздел не описывает текущие системы и не требует копировать их архитектуру. Это инструкция
для проектирования будущих игровых и интерактивных приложений с нуля или при существенном
расширении существующих проектов.

## 11.1. Сначала зафиксируй реальный масштаб

Перед выбором паттернов ответь:

1. Сколько независимых feature действительно существует сейчас?
2. Сколько сущностей одновременно обновляется?
3. Нужны ли save/load, replay, multiplayer или deterministic simulation?
4. Сколько presentation targets будет у одной логики?
5. Какие изменения вероятны в ближайших двух релизах, а не когда-нибудь?

Не выбирай ECS, EventBus, DI container, repositories или микромодули без конкретного требования.
Архитектура должна иметь запас на один правдоподобный шаг роста, а не на гипотетическую бесконечную
игру.

## 11.2. Разделяй четыре вида ответственности

Минимально полезная модель:

```text
Input
  → Application / Session
    → Domain rules and state
      → Snapshot / Events
        → Presentation
```

- **Input adapter** переводит мышь, клавиатуру, touch или сеть в намерение пользователя.
- **Application/session layer** координирует use cases и порядок систем.
- **Domain layer** хранит правила и состояние, не знает о движке и UI.
- **Presentation layer** показывает snapshot и эффекты, но не принимает бизнес-решения.

Это не Clean Architecture ради формы. Для маленького проекта каждый слой может быть одним файлом.
Важны направление зависимости и ownership, а не количество директорий.

## 11.3. Определи единственного владельца каждого факта

Для каждого состояния задай вопрос: «Кто имеет право его изменить?»

Плохие признаки:

- одно число хранится в модели и UI;
- готовность feature вычисляется тремя способами;
- сцена и simulation имеют свои версии progression;
- config, runtime и save содержат независимые defaults;
- несколько managers меняют один массив напрямую.

Хороший контракт:

```text
owner mutates state
others receive snapshot, query result or event
```

Если факт имеет двух владельцев, синхронизация рано или поздно станет отдельной скрытой системой.

## 11.4. Composition root не должен превращаться в application

Composition root отвечает за:

- создание объектов;
- передачу зависимостей;
- подключение adapters;
- запуск lifecycle.

Он не должен решать:

- можно ли совершить покупку;
- какая feature разблокирована;
- куда назначить работника;
- чем закончился игровой сценарий;
- что сохранить.

Когда bootstrap-файл начинает хранить развивающееся состояние или feature-specific conditionals,
нужен отдельный session/application object.

## 11.5. Используй команды и snapshots на границе с presentation

Практичный контракт:

```ts
interface GameSession<Command, Event, Snapshot> {
  dispatch(command: Command): CommandResult;
  tick(seconds: number): readonly Event[];
  snapshot(): Snapshot;
}
```

Presentation не должна получать прямой доступ ко всем внутренним системам. Она отправляет
намерение и показывает результат. Это облегчает:

- unit testing;
- replay;
- bots и balance simulation;
- save/load;
- замену движка или UI;
- multiplayer command validation.

Не вводи этот контракт, если приложение состоит из одного экрана без развивающегося состояния.

## 11.6. Проектируй save-compatible, но не строй save system заранее

Save-compatible означает:

- у сущностей есть стабильные IDs;
- domain-state не содержит engine objects, callbacks и timers;
- текущее время представлено данными, а не только живым таймером;
- snapshots имеют версию;
- transient visual effects не считаются сохранённым состоянием;
- state можно восстановить через явный `restore` или factory.

Не нужно заранее писать облачные сейвы, migration framework и шифрование. Достаточно периодически
доказывать round trip:

```text
state → serialize → deserialize → equivalent state
```

## 11.7. EventBus используй только для реального many-to-many

Прямой вызов предпочтительнее, когда отправитель знает единственного получателя.

EventBus оправдан, если:

- издатель не должен знать количество слушателей;
- слушатели имеют независимый lifecycle;
- сообщение является завершившимся фактом, а не скрытой командой;
- payload типизирован;
- подписки снимаются явно;
- порядок обработки либо не важен, либо формально определён.

Не используй события для обхода плохо определённого ownership. Событие `DoSomething` обычно
является замаскированной командой.

## 11.8. Не создавай интерфейс только ради одной реализации

Интерфейс полезен, когда существует хотя бы одно из условий:

- две реальные реализации;
- внешний инфраструктурный boundary;
- тестовый substitute принципиально дешевле реального объекта;
- стабильный контракт должен пережить замену технологии.

Если класс уже чистый, быстрый и детерминированный, тестировать его напрямую часто проще, чем
создавать `IClass`, factory и container registration.

## 11.9. Модули дели по причинам изменения, а не по типам файлов

Предпочтительная структура для растущего продукта:

```text
features/
  economy/
    rules
    state
    commands
    presentation-model
    tests
  construction/
  progression/
shared/
  math
  ids
  serialization
platform/
  engine
  storage
  network
```

Feature должна по возможности удаляться одной операцией без правок десятков глобальных
реестров. Shared-модуль не должен импортировать features.

## 11.10. Не выноси все числа в один глобальный config

Разделяй:

- domain rules и баланс;
- rendering/layout;
- asset identifiers;
- platform settings;
- player preferences.

Храни feature-specific значения рядом с feature, а для редактора или inspector собирай их в
registry. Registry — индекс, а не владелец всех смыслов.

## 11.11. Детерминизм должен быть архитектурным контрактом

Если игра содержит simulation, balance tests, replay или networking:

- передавай RNG как зависимость или seed;
- не используй wall clock внутри domain;
- передавай elapsed time явно;
- зафиксируй порядок обновления;
- не завязывай правила на frame rate;
- используй fixed steps там, где результат зависит от дискретизации;
- записывай команды и seed для воспроизведения.

Отдельные RNG streams полезны для независимых областей: визуальный звук не должен менять исход
боя, а декоративная случайность — экономику.

## 11.12. State machine вводи после появления состояний

FSM оправдана, когда объект имеет:

- взаимоисключающие состояния;
- явные переходы;
- разное допустимое поведение в разных состояниях;
- lifecycle `enter/tick/exit`.

Для двух boolean flags отдельная hierarchy states обычно сложнее исходной задачи. Когда
conditionals начинают повторять одну и ту же матрицу допустимых переходов, FSM становится проще.

## 11.13. ECS выбирай по данным и масштабу, а не по моде

ECS полезна при больших однотипных наборах сущностей, частых массовых запросах, требованиях к
cache locality и параллельной обработке.

ECS не является автоматическим ответом для:

- небольшого числа уникальных интерактивных объектов;
- UI-heavy игр;
- сценариев, где основная сложность — progression и workflows;
- раннего прототипа с нестабильными правилами.

Иногда обычные объекты плюс application/session layer дают более простую и надёжную систему.

## 11.14. Тестируй поведение на правильной границе

Пирамида тестов для интерактивного приложения:

1. Чистые unit tests доменных правил.
2. Workflow tests application/session без движка.
3. Contract tests сериализации, конфигов и ассетов.
4. Небольшое число engine integration tests.
5. Критические end-to-end пользовательские пути.

Не используй поиск текста в исходнике как замену behavioural test. Source tests допустимы для
статических политик — например, запрета конкретного API, проверки manifest или наличия asset key.

## 11.15. Любой крупный refactoring проводи через strangler migration

Безопасная последовательность:

```text
зафиксировать текущее поведение
→ создать узкую новую границу
→ провести через неё один vertical slice
→ сравнить старый и новый результат
→ переключить runtime
→ удалить старый путь
→ перейти к следующему slice
```

Не заменяй одновременно domain, presentation, input и content. Если rollback неизбежен, сразу
определи судьбу нового пути: удалить, завершить к дате или явно оставить экспериментом.

## 11.16. Не оставляй две реализации одного правила

Допустимый период dual-running должен иметь:

- канонического владельца;
- срок удаления второго пути;
- parity tests на одинаковых входах;
- запрет добавлять features только в одну реализацию;
- понятный runtime switch.

Если эти условия отсутствуют, параллельная архитектура — не migration, а второй продукт.

## 11.17. Документация должна различать факт, решение и намерение

Используй три явных типа документов:

- **Architecture snapshot** — что работает сейчас;
- **ADR** — почему принято решение;
- **Design/plan** — что предполагается изменить.

Не смешивай future state с текущей картой. После rollback architecture snapshot обновляется в
том же коммите. Для критических утверждений добавляй простые automated checks.

## 11.18. Правила для AI-агента перед добавлением feature

Перед изменением агент обязан ответить:

1. Кто владеет новым состоянием?
2. Через какой публичный контракт feature получает команды?
3. Кто и как наблюдает результат?
4. Нужно ли состояние сохранять?
5. Можно ли протестировать правило без UI и движка?
6. Какие существующие файлы будут меняться вместе и почему?
7. Не создаётся ли второй источник истины?
8. Не попадает ли feature-specific logic в shared/core?
9. Есть ли реальная потребность в новом abstraction layer?
10. Как удалить или заменить feature позже?

Если ответы требуют перечислить много несвязанных глобальных объектов, сначала нужна
архитектурная граница, а уже затем реализация feature.

## 11.19. Сигналы, при которых нужно остановиться и пересмотреть дизайн

- каждый новый feature требует править один и тот же центральный файл;
- исправление компиляции открывает следующую несвязанную ошибку;
- тесты вынуждены читать исходный код вместо вызова API;
- UI хранит копию domain-state;
- один manager зависит от большинства модулей;
- для теста создаётся вторая реализация настоящей логики;
- feature выключается десятками conditionals;
- save требует сериализовать engine objects;
- документация называет активным файл, не достижимый из entry point;
- временный compatibility layer получает новые features.

Это не повод немедленно переписывать всё. Это повод остановить расширение конкретной области,
восстановить dependency graph и определить новую минимальную границу.

## 11.20. Definition of Done для архитектурно значимого изменения

Изменение завершено, когда:

- существует ровно один runtime path;
- ownership состояния явно указан;
- зависимости направлены внутрь к правилам, а не наружу к framework;
- новые правила проверены behavioural tests;
- presentation проверена хотя бы одним integration path;
- old path удалён или имеет зафиксированный срок удаления;
- save compatibility рассмотрена;
- factual architecture map обновлена;
- нет новых неиспользуемых extension points;
- complexity cost решения соответствует реальному масштабу задачи.

# Финальный вывод

Главный урок истории проекта: отдельные локальные решения в основном были разумны. Системный долг
возник из-за того, что для них не существовало места между «чистой маленькой системой» и «полной
engine scene». Именно эту промежуточную границу — application/session layer — проекту стоит
достроить.

Для будущих AI-агентов главный принцип ещё шире: не начинайте с названия архитектуры. Начинайте с
ownership данных, направления зависимостей, тестируемой границы и реального следующего шага
роста. Хорошая архитектура — не та, в которой больше паттернов, а та, в которой каждое новое
требование имеет одно очевидное место и не создаёт второй источник истины.
