# Аналитика: где игроки бросают игру

Игра отправляет в Unity Analytics анонимную воронку кампании: какое задание игрок начал, какое
выполнил, чем кончился бой, и раз в минуту колонии напоминает, на каком задании он сейчас. Сохранений
нет, поэтому одна сессия — это одно прохождение: игрок ушёл на том задании, о котором было его
последнее событие.

Кто за что отвечает:

- `CampaignTelemetry` (`Runtime/Application`) читает снимки и результаты команд `GameSession` и
  превращает их в события. В правила не вмешивается; в песочнице ничего не шлёт. `Schema` в нём —
  список событий и полей, который должен совпадать с дашбордом.
- `Telemetry` (`Runtime/Support`) отправляет события, пока игрок не против: держит его выбор
  (`PlayerPrefs`), копит события до старта сервиса и выгружает их не реже раза в 10 с и при потере
  фокуса. Вкладку браузера закрывают без предупреждения, поэтому теряется не больше этих 10 с.
- `UnityAnalyticsBackend` — Unity Analytics (`com.unity.services.analytics`). Согласие идёт через
  `EndUserConsent` движка, сервис следует ему.
- `GameBootstrap` связывает одно с другим, `SupportHud` тикает и выгружает, `TechInfoPanel` показывает
  уведомление и переключатель.

В редакторе ничего не отправляется: данные дают только собранные игроки (Windows, WebGL).

## Согласие игрока

Сбор включён, пока игрок его не выключит. При первом запуске над строкой версии в правом нижнем углу
висит строка «Игра отправляет анонимную статистику…» с кнопками «Хорошо», «Не отправлять» и ссылкой
на политику Unity. Пока игрок не ответит, строка остаётся. В техпанели (F8 или клик по строке версии)
есть переключатель «Статистика: отправляется / не отправляется». Выбор хранится между запусками;
выключенная статистика даже не запускает сервис.

Если игра пойдёт туда, где нужно явное согласие до сбора (строгое прочтение GDPR), то первый запуск
спрашивает «да/нет», а `Telemetry.Collecting` по умолчанию даёт 0 вместо 1.

## События

Сервис принимает событие, только если его имя и все поля заведены в дашборде с теми же типами.
Остальное он молча выбрасывает. `TelemetryTests` проверяет, что всё отправляемое совпадает со
`CampaignTelemetry.Schema`; дашборд надо держать в согласии с этой таблицей руками.

| Событие | Когда | Поля |
|---|---|---|
| `questStarted` | старт игры и каждое новое задание (после «Забрать награду») | `questId`, `questLevel`, `activeSeconds` |
| `questCompleted` | цели задания выполнены (награда ещё не забрана) | `questId`, `questLevel`, `questSeconds`, `activeSeconds` |
| `campaignCompleted` | пройдено последнее задание авторской цепочки | `questLevel`, `activeSeconds` |
| `battleFinished` | бой рассчитан (сразу после «В бой») | `missionId`, `won`, `fallen`, `questLevel`, `activeSeconds` |
| `progressHeartbeat` | каждую минуту времени колонии | `questId`, `questLevel`, `activeSeconds`, `gold`, `buildingCount`, `unitCount` |

Поля:

| Поле | Тип | Что это |
|---|---|---|
| `questId` | string | id задания из `Progression.asset` (`tutorial-goblin`…) |
| `questLevel` | integer | номер задания в цепочке с 1; после авторской цепочки идут повторяемые |
| `activeSeconds` | integer | время колонии с начала игры; во время боя и паузы не идёт |
| `questSeconds` | integer | время колонии от начала задания до выполнения его целей |
| `missionId` | string | id миссии |
| `won` | boolean | победа игрока |
| `fallen` | integer | сколько его бойцов погибло |
| `gold` | integer | золото в казне |
| `buildingCount` | integer | построек в колонии |
| `unitCount` | integer | жителей |

Стандартные события Unity (`gameStarted`, `gameRunning`, `gameEnded`, `newPlayer`, `clientDevice`)
сервис шлёт сам. Версию игры он берёт из Player Settings (`clientVersion`).

## Настройка дашборда (один раз)

1. cloud.unity.com → проект TrollStategy → **Analytics**. Если сервис ещё не включён, включить его
   для окружения `production`.
2. **Event Manager → Custom Parameters**: завести 10 полей из таблицы выше с их типами.
3. **Event Manager → Custom Events**: завести 5 событий и отметить у каждого его поля.
4. Собрать игрока, сыграть пару минут, проверить в **Event Browser**, что события валидны. Без схемы
   они там будут с пометкой об ошибке.

Проверено 2026-10-04: проект привязан (`cloudProjectId` в сборке совпадает с дашбордом), все 5 событий и
10 полей заведены в окружении `production` с типами из таблицы. `questStarted` и `progressHeartbeat`
пришли валидными из Windows-сборки. `questCompleted` и `battleFinished` пришли валидными из Play Mode
редактора (см. «Без сборки»): бот «Обычный» прошёл задания 1–8, дошли все 9 `questStarted`,
8 `questCompleted`, 5 `progressHeartbeat` и `battleFinished` (`mission-1`, `won` в SQL читается как 1).

## Проверка

- **Где смотреть.** SQL Data Explorer показывает только принятые события. Первые видны примерно через
  минуту после отправки, остальные из того же пакета догружаются ещё несколько минут, по событиям
  вразнобой. Последние события:

  ```sql
  SELECT EVENT_TIMESTAMP, EVENT_NAME, EVENT_JSON:questId::STRING AS quest,
         EVENT_JSON:activeSeconds::INT AS secs
  FROM EVENTS
  WHERE EVENT_DATE >= CURRENT_DATE - 1
  ORDER BY EVENT_TIMESTAMP DESC;
  ```

  Отброшенные события (не совпала схема) видны только в Event Browser. Счётчики Valid/Invalid в Event
  Manager отстают: 2026-10-04 они показывали нули при данных в SQL.
- **Фокус.** `runInBackground` выключен: без фокуса окна игра стоит, время колонии не идёт, и
  `progressHeartbeat` не приходит. Сессия, открытая полчаса в свёрнутом окне, даёт только старт.
- **Без сборки.** Игра в редакторе ничего не шлёт, а сервисы Unity поднимаются только в Play Mode.
  Проверка из редактора: в Play Mode (`runInBackground` на время проверки включить) вызвать
  `UnityAnalyticsBackend.SetConsent(true)` и `StartAsync()`, затем повесить `CampaignTelemetry` на новую
  `GameSession`, отправлять через `UnityAnalyticsBackend.Record`, сыграть её ботом (`CampaignBot`,
  `StopAfterLevel = 8` даёт и бой) и вызвать `Flush()`. Такая сессия попадает в те же данные `production`
  с платформой `PC_CLIENT`.

## Страница игроков

Статистика игроков собирается так же, как у ботов: страница с графиками и файл данных рядом с ней.
Обе живут в `unity/TrollStategy/Builds/Stats` (git их не видит):

| Файл | Что это |
|---|---|
| `index.html` | общая страница: боты и игроки рядом, по ссылке в каждую |
| `bots/` | отчёт ботов (`docs/campaign-bots.md`) |
| `players/index.html` | страница игроков |
| `players/players-data.js` | её данные |
| `players/history.jsonl` | по строке на каждую сборку с новыми данными |
| `players/exports/` | сюда кладутся выгрузки из Unity |

**Обновить:**

1. Unity Dashboard → Analytics → SQL Data Explorer, окружение `production`.
2. Вставить запрос из `tools/stats/players-export.sql`, Run, затем Export (CSV).
3. Положить файл в `Builds/Stats/players/exports`. Старые выгрузки можно не удалять: событие, попавшее в
   две выгрузки, считается один раз.
4. `python tools/stats/players.py` (с `--open` откроет общую страницу). Открытая страница подхватит новые
   данные сама.

Запрос берёт четыре колонки, остальное скрипт достаёт из `EVENT_JSON` (сессию, версию, страну, поля
событий). Колонки `SESSION_ID` в таблице `EVENTS` нет, а запрос с лишними колонками SQL Data Explorer не
выполняет и просто висит. Выгрузка берёт 30 дней; для более старых данных поменять `CURRENT_DATE - 30`.

Тестовые установки разработчиков перечислены в `tools/stats/test-users.txt` и в подсчёт не попадают (страница
пишет, сколько их отсеяно); `--include-test-users` их оставляет, `--since 2026-10-10` отбрасывает события до
даты. Тесты скрипта: `python -m unittest discover -s tools/stats`.

**Что на странице:**

- плитки: игроки (и сколько вернулись), сессии, прошли кампанию, медиана последнего задания и времени в игре;
- **Воронка** — сколько сессий дошло до каждого задания, с пометкой задания, на котором заканчивается
  больше всего сессий;
- **Где заканчиваются сессии** — по последнему заданию: «не выполнил задание» (не понял, что делать) и
  «выполнил, не забрал награду» (не нашёл кнопку);
- **Время на задание: игроки и бот** — медиана и средняя половина игроков рядом с ботом «Живой игрок»;
  в таблице ещё «Обычный» и отношение к живому игроку. От ×2 стоит пометка: бот уже платит за клики и
  чтение, так что задание скорее непонятное, чем долгое;
- **Бои**, **Версии** (те же числа по сборкам), **Колония по минутам** (золото, постройки, существа против
  бота; на графике минуты, где играло хотя бы 3 сессии или 5% от всех), **Сессии**, **Выгрузки**.

У графиков есть кнопка «Таблица» и подсказки при наведении; тема общая для общей страницы и страницы игроков.

## Как читать

- **Воронка.** Страница игроков или Analytics → Funnels: шаги `questStarted` с `questLevel = 1, 2, 3…`.
  Самая большая ступенька вниз — задание, на котором уходят.
- **Застрял или ушёл довольным.** Если у задания много `questStarted` и мало `questCompleted`, игрок
  не понял, что делать. Если `questCompleted` есть, а следующего `questStarted` нет, он не нашёл
  «Забрать награду».
- **Сравнение с ботами.** `questSeconds` у живых игроков против `DurationMs` того же задания у ботов —
  на странице игроков это график «Время на задание» (данные ботов — `Builds/Stats/bots`, см.
  `docs/campaign-bots.md`). Если игрок тратит в 3–4 раза больше обычного бота или в 2 раза больше бота
  «Живой игрок», задание непонятное, а не долгое.
- **Бои.** Доля `won = false` и `fallen` по `missionId` и `questLevel` показывают, не упирается ли
  уход в проигранный бой.
- **Где кончилась сессия.** Data Explorer → SQL:

  ```sql
  -- последнее задание каждой сессии и сколько сессий на нём кончилось
  WITH last AS (
    SELECT EVENT_JSON:sessionID::STRING AS session, MAX(EVENT_JSON:questLevel::INT) AS level
    FROM EVENTS
    WHERE EVENT_NAME IN ('questStarted', 'questCompleted', 'progressHeartbeat')
      AND EVENT_DATE > CURRENT_DATE - 14
    GROUP BY session
  )
  SELECT level, COUNT(*) AS sessions
  FROM last
  GROUP BY level
  ORDER BY level;
  ```

В SQL Data Explorer события видны примерно через минуту; готовые графики дашбордов обновляются реже.

## Изменить события

Новое событие или поле — это правка в трёх местах сразу: `CampaignTelemetry` (и его `Schema`), эта
таблица и Event Manager. Если поменять тип поля, у которого уже есть данные, дашборд не даст: заводят
новое поле с новым именем.
