# Аналитика: где игроки бросают игру

Игра отправляет в Unity Analytics анонимную воронку кампании: какое задание игрок начал, какое
выполнил, чем кончился бой, и раз в минуту колонии напоминает, на каком задании он сейчас. Сохранений
нет, поэтому одна сессия — это одно прохождение: игрок ушёл на том задании, о котором было его
последнее событие.

Кто за что отвечает:

- `CampaignTelemetry` (`Runtime/Application`) читает снимки и результаты команд `GameSession` и
  превращает их в события. В правила не вмешивается; в песочнице ничего не шлёт. `Schema` в нём —
  список событий и полей, который должен совпадать с дашбордом.
- `Telemetry` (`Runtime/Support`) отправляет события, пока игрок не против: держит его выбор
  (`PlayerPrefs`), копит события до старта сервиса и выгружает их не реже раза в 10 с и при потере
  фокуса. Вкладку браузера закрывают без предупреждения, поэтому теряется не больше этих 10 с.
- `UnityAnalyticsBackend` — Unity Analytics (`com.unity.services.analytics`). Согласие идёт через
  `EndUserConsent` движка, сервис следует ему.
- `GameBootstrap` связывает одно с другим, `SupportHud` тикает и выгружает, `TechInfoPanel` показывает
  уведомление и переключатель.

В редакторе ничего не отправляется: данные дают только собранные игроки (Windows, WebGL).

## Согласие игрока

Сбор включён, пока игрок его не выключит. При первом запуске над строкой версии в правом нижнем углу
висит строка «Игра отправляет анонимную статистику…» с кнопками «Хорошо», «Не отправлять» и ссылкой
на политику Unity. Пока игрок не ответит, строка остаётся. В техпанели (F8 или клик по строке версии)
есть переключатель «Статистика: отправляется / не отправляется». Выбор хранится между запусками;
выключенная статистика даже не запускает сервис.

Если игра пойдёт туда, где нужно явное согласие до сбора (строгое прочтение GDPR), то первый запуск
спрашивает «да/нет», а `Telemetry.Collecting` по умолчанию даёт 0 вместо 1.

## События

Сервис принимает событие, только если его имя и все поля заведены в дашборде с теми же типами.
Остальное он молча выбрасывает. `TelemetryTests` проверяет, что всё отправляемое совпадает со
`CampaignTelemetry.Schema`; дашборд надо держать в согласии с этой таблицей руками.

| Событие | Когда | Поля |
|---|---|---|
| `questStarted` | старт игры и каждое новое задание (после «Забрать награду») | `questId`, `questLevel`, `activeSeconds` |
| `questCompleted` | цели задания выполнены (награда ещё не забрана) | `questId`, `questLevel`, `questSeconds`, `activeSeconds` |
| `campaignCompleted` | пройдено последнее задание авторской цепочки | `questLevel`, `activeSeconds` |
| `battleFinished` | бой рассчитан (сразу после «В бой») | `missionId`, `won`, `fallen`, `questLevel`, `activeSeconds` |
| `progressHeartbeat` | каждую минуту времени колонии | `questId`, `questLevel`, `activeSeconds`, `gold`, `buildingCount`, `unitCount` |

Поля:

| Поле | Тип | Что это |
|---|---|---|
| `questId` | string | id задания из `Progression.asset` (`tutorial-goblin`…) |
| `questLevel` | integer | номер задания в цепочке с 1; после авторской цепочки идут повторяемые |
| `activeSeconds` | integer | время колонии с начала игры; во время боя и паузы не идёт |
| `questSeconds` | integer | время колонии от начала задания до выполнения его целей |
| `missionId` | string | id миссии |
| `won` | boolean | победа игрока |
| `fallen` | integer | сколько его бойцов погибло |
| `gold` | integer | золото в казне |
| `buildingCount` | integer | построек в колонии |
| `unitCount` | integer | жителей |

Стандартные события Unity (`gameStarted`, `gameRunning`, `gameEnded`, `newPlayer`, `clientDevice`)
сервис шлёт сам. Версию игры он берёт из Player Settings (`clientVersion`).

## Настройка дашборда (один раз)

1. cloud.unity.com → проект TrollStategy → **Analytics**. Если сервис ещё не включён, включить его
   для окружения `production`.
2. **Event Manager → Custom Parameters**: завести 10 полей из таблицы выше с их типами.
3. **Event Manager → Custom Events**: завести 5 событий и отметить у каждого его поля.
4. Собрать игрока, сыграть пару минут, проверить в **Event Browser**, что события валидны. Без схемы
   они там будут с пометкой об ошибке.

## Как читать

- **Воронка.** Analytics → Funnels: шаги `questStarted` с `questLevel = 1, 2, 3…`. Самая большая
  ступенька вниз — задание, на котором уходят.
- **Застрял или ушёл довольным.** Если у задания много `questStarted` и мало `questCompleted`, игрок
  не понял, что делать. Если `questCompleted` есть, а следующего `questStarted` нет, он не нашёл
  «Забрать награду».
- **Сравнение с ботами.** `questSeconds` у живых игроков против `DurationMs` того же задания у ботов
  (`Builds/Bots/<profile>.md`, см. `docs/campaign-bots.md`). Если игрок тратит в 3–4 раза больше
  обычного бота, задание непонятное, а не долгое.
- **Бои.** Доля `won = false` и `fallen` по `missionId` и `questLevel` показывают, не упирается ли
  уход в проигранный бой.
- **Где кончилась сессия.** Data Explorer → SQL:

  ```sql
  -- последнее задание каждой сессии и сколько сессий на нём кончилось
  WITH last AS (
    SELECT SESSION_ID, MAX(EVENT_JSON:questLevel::INT) AS level
    FROM EVENTS
    WHERE EVENT_NAME IN ('questStarted', 'questCompleted', 'progressHeartbeat')
      AND EVENT_DATE > CURRENT_DATE - 14
    GROUP BY SESSION_ID
  )
  SELECT level, COUNT(*) AS sessions
  FROM last
  GROUP BY level
  ORDER BY level;
  ```

Данные в дашборде появляются с задержкой (обычно несколько часов).

## Изменить события

Новое событие или поле — это правка в трёх местах сразу: `CampaignTelemetry` (и его `Schema`), эта
таблица и Event Manager. Если поменять тип поля, у которого уже есть данные, дашборд не даст: заводят
новое поле с новым именем.
